# Lessons learned

- 7Pace Timetracker uses its own API token (created in ADO under Time Tracker > Settings > API Tokens), separate from an Azure DevOps PAT — do not conflate the two.
- The exact 7Pace `workLogs` POST payload shape (`timestamp`, `length` in seconds, `comment`) is a best-effort guess carried over from an earlier PowerShell prototype and is unverified against a live instance's Swagger docs (`https://<org>.timetracker.7pace.com/api/rest/help`) — confirm before relying on it in production.
- Context7 MCP server was not connected in this session, so 7Pace API docs could not be looked up through it; fell back to best-known API patterns instead.
- Because other iCore staff will use this app with different work items, the app must ship with zero hardcoded/pre-seeded work items — each installation's `workitems.json` (under `%AppData%`) starts empty and is filled via a mandatory first-run wizard.
- Plan deviation: spec's "open settings dialog automatically on 401" simplified to per-row error + menu access (documented in plan self-review).
- .NET 10 SDK 'dotnet new sln' emits .slnx (XML) not .sln; functionally equivalent, avoid hard-coding .sln extension in CI.
- Namespaces can't start with a digit: 7PaceDesktop.* projects use RootNamespace PaceDesktop.*
- 7Pace workLogs payload shape (Bearer auth, api-version=3.2, length in seconds) is UNVERIFIED against a live instance; pinned by tests, must be confirmed live in Task 10 before real use.
- v1 limitation: PaceApiClient is built once at startup, so org/token changes via the in-app settings dialog only take effect after an app restart.
- 7Pace CLOUD REST API (verified vs official docs 2026-07-03): base is https://{account}.timehub.7pace.com/api/rest/workLogs?api-version=3.2 (NOT timetracker.7pace.com). {account} = the Azure DevOps org (e.g. "icore"), never the project. Create-worklog body: { workItemId:int, timeStamp:ISO8601 (capital S), length:seconds:int, optional comment/billableLength/userId/activityTypeId }. Auth: Authorization: Bearer {token} from 7Pace Settings > Reporting and API. Find your exact API URL there.
- Credential-Manager-backed xUnit tests must share one [Collection] — concurrent real Credential Manager access races and fails intermittently even with unique keys.
- WPF-UI theming on plain Windows: set Background={DynamicResource ApplicationBackgroundBrush} and TextElement.Foreground={DynamicResource TextFillColorPrimaryBrush} on each Window so dark mode renders correctly without converting to FluentWindow. Grid row highlights use translucent ARGB tints (#33.., #40..) so they read on both light and dark.
- WPF-UI 4.x does NOT implicitly restyle stock WPF controls (only its own ui:* controls) — merging its dictionaries + setting a dark window background left stock labels/menu black-on-black. For this app we ship a self-contained Palette.Light/Dark + implicit-style Styles.xaml over stock controls instead; ThemeService swaps the palette dict and reads HKCU AppsUseLightTheme for System. Verify WPF UI changes with a PrintWindow (flag 2) screenshot — SetForegroundWindow capture grabs whatever is on top.
- 7Pace read API (docs-verified 2026-08-28, response fields still UNVERIFIED live): GET {account}.timehub.7pace.com/api/rest/workLogs?api-version=3.2 with $fromTimestamp/$toTimestamp/$count (max 500)/$skip is scoped to the CURRENT USER; /workLogs/all is org-wide; also GET /me, PATCH /workLogs/{id}, DELETE /workLogs/{id}.
- Safety rule for gap-aware generation: a failed worklog fetch must yield an explicit "unknown" day state that BLOCKS registration — treating unfetched days as zero would double-log real time.
- Design-canvas mockups: bash heredocs choked on the large generator script; write generator files with the Write tool instead. Lift WPF theme values straight from Themes/Palette.*.xaml into CSS custom properties so light/dark mockups match the real app.
- Calendar redesign decisions locked: ledger-style day cells (logged / expected + work item IDs) over deficit-style; bulk registration stays first-class — drag-select, week-number gutter, "Alla tomma dagar", one Registrera for the whole set.
- Calendar plan rules settled in the spec: NonWorking beats Unknown (schedule is known locally, so a weekend stays a weekend during a failed fetch), and fill lines scale by remaining/target so partial days and short pre-holiday days use one code path.
- 7Pace GET response field names AND the timeStamp timezone must be confirmed with one live call before release — the POST contract was wrong on both host and field casing the first time, so this is a release gate, not a nice-to-have.
- Stack-change assessment for the calendar redesign: recommendation is to stay on WPF — Core/planner tasks are UI-agnostic, nothing in the design needs non-WPF rendering, the custom Palette+Styles theme already solves the theming problem WPF-UI failed at, and Credential Manager token storage is .NET-native. Avalonia is the only defensible switch, and only if non-Windows clients are required.
- Stack decision reversed to a locally-run web app (ASP.NET Core Minimal API + React/Vite/Tailwind, single-file win-x64 exe): the user wanted a nicer UI and does not care about the stack. Core C# is kept verbatim so the verified 7Pace client, holidays, storage and credentials are not rewritten.
- A browser-only 7Pace app is not viable: the token would move from Windows Credential Manager into browser storage, and the 7Pace API almost certainly sends no CORS headers for a localhost origin. Hence a local server that holds the token and serves the SPA.
- Local-API security bar: bind 127.0.0.1, configure NO CORS policy, and require header X-Pace-Client:1 on every mutating endpoint — the custom header forces a preflight that a cross-origin page cannot pass.
- Planning arithmetic stays in C# only. The front end may compute max(0, expected-logged) and sums of it; the split/rounding rules live solely in FillPlanner so preview and posted values cannot drift.
- Register endpoint refetches worklogs and rebuilds the plan before posting, returning 409 if that read fails — makes client staleness impossible instead of policing it in the UI.
- Server endpoint tests need an ITokenSource seam; without it every WebApplicationFactory test reads and writes the developer's real Credential Manager entry.
- Bash heredocs truncate on large content in this environment (failed twice around 100-140 lines). Write long files with the Write tool, or write a part file and `cat >>` it.
- Plan self-review pays off on component-signature drift: a later task that adds props to a React component silently invalidates the render() calls in an earlier task's test file — check every cross-task type and prop change before handing a plan to executors.
- Subagent prompts for this plan must carry: the task's own section verbatim, the Global Constraints section, the token-never-in-a-response rule, and the "planning arithmetic stays in C#" rule — subagents get no session-start memory injection and cannot see the plan header.
